# 四个开源项目实跑：何时该让一个 Agent 把事情做完？

**对于需要把刚查到的事实用于下一步决策的短任务，先用一个主 Agent 和可靠的业务工具。** 在两个有单／多 Agent 对照的项目里，单循环的总模型调用都少了，必要的任务结果没有变差。只有一个小面板显示最终说明也更完整，不能推出普遍成功率更高。需要单独维护的政策与流程，可以让主 Agent 按需读取；是否另开一个 Agent，要看独立上下文能带来什么实测收益。

[Anthropic 原文](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)谈的是现有专家分工值不值得保留：知识可以分开维护，执行同一项决策所需的信息却可能散落在多个上下文中；它也保留了并行研究、独立核验和隔离权限等正当理由。只有下表前两个项目直接比较了折回主循环。后两个用来查另一件同样关键的事：即使模型知道该做什么，业务系统到底做了什么。

| 在哪个项目上做了什么 | 本机实际结果 | 选用价值 |
|---|---|---|
| [Anthropic 官方 kit](kit/README.md)：相同授权、业务读写工具和条件任务，换三种决策路径；再跑原版两套应用 | 自由交接、给同一专家附原文和回执、主循环直接执行，严格判分各 **6/6**；模型调用 **25／25／16**。原版 t11 在相同 14 次调用上限下，旧系统已开单但未答复，完成版用 3 次开单并交回 RMA。 | **迁移现有多 Agent 首选的实验起点**。保留其逐步迁移和重放方法，自己补上重复写、越权写、负例与最终回执判分。 |
| [hatyibei 日语电商](haty/README.md)：原版专家 A、只给退货专家补物流工具 A1、所有工具与按需手册在主循环 B；三道原题各两次 | 上游确定性判分和本地查证据均 **6/6、6/6、6/6**。预先指定的最终说明覆盖 **5/6、2/6、6/6**；模型调用 **42／32／28**。A1 的专家查对了，协调者也收到了，仍会省略签收日或政策期限。 | **比较“补专家接口”还是“收回决策”的最佳小对照**。真正应区分的是能否查到、决策者是否收到、最后是否用上。补权限既非无效，也不自动保证最后一步。 |

## 哪条结论改变了原来的看法

以日语退货为例：客户问“还来得及退吗？”需要订单、签收日和政策。对同一道题，两次完整运行分别是：

| 路线 | 模型调用（两次） | 顾客最终知道了什么 |
|---|---:|---|
| 协调者找专家，退货专家不能查物流 | 10、14 | 签收 9/28、最晚 10/28 均说明。第二次先找退货、再找物流、又回退货，三次验证身份和查单。 |
| 仍由专家办理，只给退货专家物流工具 | 6、6 | 少了绕路。两次专家都查出 9/28 和期限，协调者也收到，但最终回复只给截止日。 |
| 主循环直接查所需资料 | 5、5 | 两次都给了签收日和截止日。 |

如果业务验收只要求“能否退、最晚哪天”，不能把第二组说成错误退货。若要求向客户解释日期依据，漏项就是真问题。相反，对已开封且不适用退款的另一题，A 用 **5 次**调用就正确拒绝；A1 和 B 都花 **6 次**并查了具体物流日期。应先约定客户到底需要哪种结果，再谈“做得更好”。用某一组的答法倒推金标，会偏袒那一组。

[附实验：LangChain 的 SQL Skills 教程](langchain-reference/README.md)专门解决另一个混淆。两道公司口径题，**读原版 Skill 2/2、普通工具返回相同正文 2/2、不给资料 0/2**；每条 SQL 都在两份数据上执行。不给资料时模型追问口径。它支持资料需可达，不支持只有 Skills 才能传达。Skill 是供模型读的知识或流程；工具是可调用的接口，可以查事实、执行动作，也可以用来加载 Skill。**加载手册不会产生第二个决策者。** 这一附实验使用 LangGraph 上的 LangChain；四个项目中的原版主循环并未统一改写成 LangGraph。

## 怎么用于下一个业务场景

1. **先给一项具体任务写验收。** 例如“ETA 晚于周五才退另一笔订单”：列出所需的订单身份、真实 ETA、比较条件、准许写的订单、唯一回执。配一对文字相同但 ETA 不同的样本，有一半必须不写。既查后台账本，也查客户最后收到什么。
2. **在同一题、同一工具和模型下找差异。** 已有多 Agent，保留现状作对照，只补专家缺的工具或原始证据，再试把该决策折回主循环。新建业务，优先用单循环和清楚的工具说明作起点。资料可独立更新、较长、只在部分任务用时，另测按需读取，以及普通查询接口提供相同知识的对照。测失败发生在取数、交接、使用、写入还是答复，不只比总分。
3. **对子 Agent 采用它真正可能获胜的题。** 例如同一时限分别调查多个独立供应源，比较经去重、有出处的新增发现与端到端时间；或让独立核验者检测预埋错误，同时统计误报。固定总资源、配全量真实流量中的普通题和留出题，达成约定质量再比耗时及费用。**这四个项目的新实验没有证明增加子 Agent 能查得更全、做得更快或验证更可靠，也没排除这些收益。**

## 哪些是证据，哪些不是

- 四个上游均固定提交；原生工程测试、作者旧记录复算、我们新做的真实模型试验和脚本化故障注入在各报告拆开。四项目新增 **52 次任务运行、229 次真实模型请求**（83＋102＋6＋38）；SQL 附项另有 6 次任务／10 次请求，连通性另有 1 次请求。重复不当作独立新题。之前本仓四配置各 24/24 的[留出实验](../../FAIR-RESULTS.md)是另一批数据。
- 模型统一经同一登录态 Codex CLI（gpt-6.1-sol、low）决定答复和工具调用；业务函数、状态和交接由各项目代码执行。桥接共用提示明确“取得回执才宣称成功”，对各组相同，可能提高绝对成功率。不等同原生 Claude、模型托管工具搜索、思考预算、流式性能、原生 token 上限、延迟或计价。调用次数仅作具体实现的工作量；不跨项目比绝对耗时、tokens 或美元。
- 合成店铺／通知与只读 SQLite，不涉及真实客户或对外写；真实支付、更长历史、海量工具、多人并行、生产业务收益没有测。部分题公开、较简单、每格最多两次；没有预注册显著性检验，也没有对所有实现寻找理论最优。主要发现来自可重演的调用、已见事实、实际状态变化，不是一个排行榜。
- [跨项目回执核验](verify.py)核对原始 CLI 完成事件、四份任务结果、缓存口径与冻结文件；[机器摘要](EVIDENCE.json)。原始请求／回复、虚拟环境、第三方源码归档都留在忽略的 runs。运行时入口与传输固定在本地 Git **3e77b65**；交付稿整理排版并补入离线核验和复跑文档。四个上游的原仓没有修改。
