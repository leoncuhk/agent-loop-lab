# Agent Loop Lab

**知识可以按领域分开维护；同一项业务决定，优先让一个主 Agent 做完。** 对于“查到一个事实，再按用户的条件行动”的任务，我们观察到的好处是：同样办对，少几次模型往返。没有证据表明，把每个业务领域都配成一个专家 Agent，会让这类任务更准确。

例如，用户说：“新设备晚于周五到，才退旧设备。”物流团队可以维护到货查询，售后团队可以维护退货手册；决定退不退的人需要同时看到用户说的“才”、实际到货日期和要退的订单。**分开维护知识，并不要求分开做决定。**

### 为什么优先用一个主 Agent？

同一个模型使用同一套业务工具，分别由主 Agent 直接办、交给专家办、交给专家并附上原请求与查询回执。三种方式都 **6/6 办对**：该写入时写一次，不该写入时不动，并正确答复用户。主 Agent 直接执行共用 **16 次模型调用**，两种专家方案各用 **25 次**。这支持“短任务少一次交接可以省调用”，并没有证明专家办不对。[配对结果及判分规则](fieldwork/2026-11-08/kit/README.md)

另一组冻结后的 12 道采购、修订和账务题，每题跑两遍。只给工具、全量读手册、按需读手册、允许委派，四种配置都是 **24/24 首次通过**。工具组用的 tokens 最少；可委派组实际只在 6/24 次中启动了子 Agent。因此这组结果支持从简单方案起步，不能据此断言不同架构普遍等效。[正式结果](FAIR-RESULTS.md)

### Skill 什么时候有用？

业务有专门口径时，先让做决定的 Agent **取得正确资料**。两道涉及公司规则的 SQL 题，用 Skill 读规则，两题都答对；普通查询工具返回逐字相同的规则，也都答对。没有资料时，模型两次都询问定义，未交付正确查询。这里起作用的是规则可得，Skill 是提供它的一种方式。[SQL 执行结果](fieldwork/2026-11-08/langchain-reference/README.md)

按需读取还有一个独立价值：少带无关内容。在提供 24 份手册的那批任务中，按需读取比全量加载平均少用 **31.5% tokens**，通过数相同；在只有 3 份手册的另一批题上，按需反而多用 **1.7%**。每批内部是同题对照，两批题目不同，不能把手册数量当作通用分界线。[配对用量](reports/fair-v2-resource-comparison.json)

### 什么情况下值得拆 Agent？

先看交接能否保住用户真正需要的东西。日语退货案例中，给退货专家补上物流查询工具后，它两次都查到了“9 月 28 日签收，10 月 28 日截止”，协调者也收到了这两个日期，却两次都只告诉客户截止日。主 Agent 直接办理时，两次都说明了日期依据。如果客户只需要截止日，两种答复都正确；如果还要解释怎么算出来，前者就少交付了一项。[逐题轨迹核验](fieldwork/2026-11-08/haty/README.md)

**选型建议：先以「一个主 Agent＋可靠工具」作基线。** 缺业务知识就补资料；退款、改价等动作让工具在执行时校验权限和当前状态。只有当工作适合独立并行、需要隔离权限或独立核验时，再考虑子 Agent。若理由是更快、更全或更可靠，就在同预算下分别测总耗时、经核实的新增发现或检错率。本项目尚未证明子 Agent 在这些场景中的净收益。

这些判断来自单一模型和合成业务任务，不是生产成功率或账单节省承诺。研究问题源于 [Anthropic 的文章](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)。
